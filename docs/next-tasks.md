# کارهای باقی‌مانده — به ترتیب اجرا

هر بخش یک واحد کار مستقل است. ترتیب مهم است. بعد از هر کدام، `make check` باید
سبز باشد و باید commit بزنی قبل از رفتن به بعدی.

---

## کار ۰ — تأیید وضعیت فعلی (اول از همه)

قبل از نوشتن هر خط کد جدید:

```bash
pip install -e ".[dev]"
alembic upgrade head
pytest -q
lint-imports
mypy src
```

`docs/security.md` از ۴۰ تست شکست‌خورده حرف زده بود. اگر هنوز قرمزند، **قبل از
هر کار جدید** رفعشان کن و گزارش بده چه چیزی خراب بود. نتیجه‌ی این مرحله تعیین
می‌کند بقیه‌ی کارها روی زمین محکم ساخته می‌شوند یا نه.

## کار ۱ — روترهای گم‌شده‌ی ادمین

پنل ادمین شش بخش دارد که هیچ API ندارند. بدون این‌ها حتی نمی‌شود یک نود اضافه
کرد، یعنی کل زنجیره‌ی provisioning غیرقابل استفاده می‌ماند.

بساز:

| روتر | اندپوینت‌ها |
|---|---|
| `admin_panels.py` | CRUD نود + `POST /{id}/test-connection` |
| `admin_orders.py` | فهرست با فیلتر، جزئیات، `POST /{id}/retry-provision` |
| `admin_subscriptions.py` | فهرست، جزئیات، `POST /{id}/sync-usage` |
| `admin_customers.py` | فهرست کاربران نهایی، جزئیات، مسدودسازی |
| `admin_broadcast.py` | ساخت، زمان‌بندی، پیشرفت |

نکات:

- `test-connection` واقعاً باید `PanelProvider.for_node()` را صدا بزند و لاگین
  کند. دکمه‌ای که فقط `base_url` را ping می‌کند بی‌فایده است.
- رمز پنل **هرگز** در پاسخ برنگردد. در schema فقط `has_password: bool`.
- `retry-provision` باید `ProvisioningService.provision()` را صدا بزند —
  idempotent است، پس فشار دادن دوباره‌ی دکمه بی‌خطر است.
- مجوزها از `domain/identity/permissions.py` بیایند، رشته‌ی جدید نساز.
- برای هر روتر یک تست integration در `tests/integration/`.

## کار ۲ — هم‌راستاسازی قرارداد ادمین

`admin/src/lib/api.ts` مسیرهایی صدا می‌زند که با بک‌اند فرق دارند:

| فرانت | بک‌اند |
|---|---|
| `/admin/session` | `/admin/auth/login` |
| `/admin/dashboard` | `/admin/analytics/dashboard` |
| `/admin/categories`, `/products`, `/plans`, `/coupons` | زیر `/admin/catalog/` |
| `/admin/duration-ladder` | وجود ندارد |

**یک طرف را انتخاب کن و همه‌جا اعمالش کن.** پیشنهاد: بک‌اند را تغییر نده (تست
دارد)، فرانت را اصلاح کن. هر تصمیمی گرفتی در `docs/api-contract.md` بنویس.

بعدش یک تست بنویس که این وضعیت دوباره تکرار نشود: مسیرهای فراخوانی‌شده در
`admin/src` را از فایل‌ها استخراج کند و با `app.routes` مقایسه کند. اگر
اختلافی بود، تست قرمز شود.

## کار ۳ — بک‌اند مینی‌اپ

مینی‌اپ ۱۶ اندپوینت زیر `/api/miniapp/*` صدا می‌زند که هیچ‌کدام وجود ندارند.

اول تصمیم احراز هویت: مینی‌اپ هدر `Authorization: tma <initData>` می‌فرستد ولی
بک‌اند مدل JWT دارد (`POST /auth/telegram/mini-app`). یا یک dependency بنویس که
`tma` را بپذیرد و همان مسیر تأیید `initData` را استفاده کند، یا فرانت را به
JWT ببر. اولی به تجربه‌ی کاربر نزدیک‌تر است.

خبر خوب: بیشتر این‌ها read model هستند و معادلشان در
`application/bot/read_models.py` از قبل وجود دارد. سرویس جدید ننویس؛ همان‌ها را
از یک روتر دیگر در معرض بگذار.

اندپوینت‌ها را از اینجا بگیر:

```bash
grep -rhoE "'/api/miniapp/[^']*'" miniapp/src | tr -d "'" | sort -u
```

## کار ۴ — readerهای SQL برای broadcast و campaign

دو job زمان‌بندی‌شده در `entrypoints/worker.py` عمداً ثبت نشده‌اند چون
`BroadcastService` و `CampaignService` هرکدام یک reader می‌خواهند که پیاده‌سازی
SQL ندارد.

الگویش `SqlSubscriptionReader` در
`infrastructure/persistence/repositories/subscription_reader.py` است — همان را
دنبال کن: فیلتر در SQL، سقف روی تعداد، و ساختن snapshot به‌جای aggregate.

بعد در `worker.py` ثبتشان کن و کامنتی که توضیح می‌دهد چرا ثبت نشده‌اند را بردار.

## کار ۵ — همگام‌سازی مصرف با پنل

هیچ‌جا مصرف ترافیک از پنل خوانده نمی‌شود، یعنی
`SubscriptionModel.traffic_used_mib` همیشه صفر می‌ماند و یادآور حجم هرگز شلیک
نمی‌شود.

یک job جدید در worker که برای هر نود فعال، `PanelAdapter.fetch_usage()` را صدا
بزند و اشتراک‌ها را به‌روز کند. حواست به این باشد:

- به‌ازای هر نود یک درخواست دسته‌ای، نه یکی به‌ازای هر مشتری.
- نودی که در دسترس نیست نباید بقیه را متوقف کند.
- `account_count` روی نود را هم از همین‌جا تصحیح کن (کامنتش در
  `SqlAlchemyNodeRepository.record_account_added` هست).

## کار ۶ — بدهی‌های باقی‌مانده

به ترتیب اهمیت:

1. **تست برای analytics** — فاز ۱۱ صفر تست دارد و ماژول‌هایش عدد پول تولید
   می‌کنند. از `domain/analytics/` شروع کن.
2. **اعمال رمزنگاری روی ستون‌های موجود** — مکانیزم آماده است، ولی مدل‌های
   کارت بانکی و توکن هنوز `EncryptedString` نیستند. مایگریشن backfill لازم دارد.
3. **enroll کردن recovery code برای 2FA** — ساخته می‌شوند، هیچ‌جا به کاربر داده
   نمی‌شوند.
4. **attachment تیکت** — ستون فایل و مسیر آپلود ندارد.
5. **Outbox واقعی** — `DispatchingEventPublisher` الان درون-تراکنشی است. seam
   درست است؛ فقط پیاده‌سازی باید عوض شود.

## سبک کار پیشنهادی با Claude Code

**یک کار در هر session.** این پروژه دقیقاً به‌خاطر «همه‌چیز را با هم بساز» به
این وضع افتاد.

**اول بخوان، بعد بنویس.** هر session را با این شروع کن:
> قبل از هر تغییری، `CLAUDE.md` و بخش مربوطه در `docs/phase-audit.md` را بخوان.
> بعد بگو چه فایل‌هایی را قرار است تغییر دهی و چرا. صبر کن تأیید کنم.

**تست را خودش اجرا کند.** بزرگ‌ترین مزیت Claude Code نسبت به چت همین است. در
پرامپت بگو:
> بعد از هر تغییر `make check` را اجرا کن. اگر قرمز شد، خودت رفع کن و دوباره
> اجرا کن. تا سبز نشده نگو تمام شد.

**نگذار خودش تأیید کند که کار کرده.** هر ادعایی باید با خروجی یک دستور همراه
باشد. اگر گفت «حالا کار می‌کند»، بپرس کدام تست این را نشان می‌دهد.

**بعد از هر کار commit بزن** با پیامی که می‌گوید چه چیزی وصل شد، نه فقط چه
فایلی اضافه شد.
